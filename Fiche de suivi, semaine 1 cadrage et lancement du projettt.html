Fiche de suivi, semaine 1 : cadrage et lancement du projet

Projet : Agent de diagnostic de logs CI/CD Nov 16, 2026 · @Larhlimi

Mode d'emploi

Cette fiche fixe votre projet et prouve que le groupe a démarré : elle compte pour 5 points sur 100. Les fiches des semaines 2 et 3 comptent chacune pour 10 points.

  • Une seule fiche par groupe, remplie ensemble et relue par chaque membre.
  • Dépôt de la fiche : docs/suivi/fiche-semaine-1.md dans le dépôt GitHub du groupe (push S1-6 de la liste des push).
  • Date limite : fin de la semaine 1 du projet, à la date annoncée en séance.
  • Réponses courtes et vérifiables : un chiffre, un lien ou un nom de fichier valent mieux qu'une phrase générale.
  • Si un point n'est pas encore tranché, écrivez « à décider » et la date de décision, plutôt que de laisser la case vide.

Rappel du barème du projet, sur 100 : application finale 20, dépôt GitHub 20, fiches hebdomadaires 25 (5 + 10 + 10), soutenance 20, compte rendu 15.

2. Sujet et besoin

Question Votre réponse
Besoin en une phrase Réduire de 30–60 min à moins de 30 s le diagnostic d'un pipeline CI/CD échoué, avec cause probable, extraits de logs et documentation cités.
Utilisateur final : qui se sert de l'application Développeur ou ingénieur DevOps d'une équipe de développement.
Ce que fait l'application, vu par l'utilisateur (3 lignes au plus) L'utilisateur colle un log de pipeline échoué. L'agent extrait les erreurs, cherche la documentation/runbooks pertinents et affiche un diagnostic structuré avec citations et étapes de correction. L'historique des diagnostics est consultable.
Approche retenue (règles, apprentissage, RAG, agent) et raison du choix RAG + agent : le LLM raisonne sur du texte technique, la recherche vectorielle ancre le diagnostic dans la documentation réelle et permet de citer les sources.
Conséquence d'une erreur de l'application, et validation humaine prévue Un diagnostic erroné peut orienter vers une mauvaise correction. L'agent ne modifie jamais le code : l'ingénieur valide et applique lui-même la correction proposée.
Sujet hors catalogue : projet du catalogue auquel il est comparable Comparable au sujet catalogue n° 7 (agent de recherche documentaire) : même pipeline RAG, spécialisé sur les logs DevOps.

3. Périmètre

La version minimale est le parcours complet le plus simple, de la demande de l'utilisateur jusqu'à la réponse affichée. Elle doit fonctionner à la fin de la semaine 2.

Rubrique Votre réponse
Version minimale : le parcours que vous montrerez en semaine 2 Coller un log → parser → recherche vectorielle → appel LLM → diagnostic JSON avec citations affiché dans Streamlit.
Fonction 1, indispensable Ingestion et analyse de logs : extraction des erreurs et segmentation par étape du pipeline.
Fonction 2, indispensable Diagnostic avec citations : cause probable + extraits de logs + documents sources + corrections suggérées.
Fonction 3, si le temps le permet Interface web de soumission et d'historique des diagnostics.
Hors périmètre : ce que vous ne ferez pas Pas d'intégration API aux plateformes CI (GitHub Actions, GitLab CI), pas de correction automatique du code, pas de multi-utilisateurs ni de droits, pas d'analyse temps réel.

5. Données

Règle du cours : uniquement des données publiques, fictives ou anonymisées.

Question Votre réponse
Origine des données (source, licence) Logs publics de projets open source (builds GitHub Actions échoués, licence MIT/Apache) + documentation publique GitHub Actions / GitLab CI (CC BY).
Volume disponible aujourd'hui ~100 fichiers de logs (≈ 10 000 lignes) + ~50 pages de documentation.
Format Logs .txt / .log (lignes horodatées, étapes, erreurs) ; docs Markdown.
Données personnelles : non, ou oui avec la méthode d'anonymisation Non ; anonymisation des noms d'utilisateurs et URLs internes si nécessaire (script de remplacement).
Jeu d'essai versionné dans le dépôt : chemin du fichier ou du script data/sample/ (échantillon < 10 Mo) ; script de collecte scripts/collect_logs.py.

Description du jeu de données

Vue d'ensemble :

Caractéristique Votre réponse
Ce que représente une ligne (ou un document) Un fichier de log = un build CI/CD échoué ; un document = une page de documentation/runbook.
Nombre de lignes ou de documents ~100 fichiers de logs (≈ 10 000 lignes) + ~50 documents.
Nombre de variables (colonnes) Logs non tabulaires : timestamp, étape, niveau, message (4 champs extraits par le parser).
Période couverte et langue 2023–2026 ; anglais majoritaire, français minoritaire.
Variable cible ou réponse attendue, s'il y en a une Cause attendue du diagnostic + documents/passages attendus (jeu de test de 20 cas).
Répartition de la cible : effectif par classe, ou minimum, moyenne et maximum À décider (date : 20/11/2026) après labellisation des 20 cas de test.
Pour un corpus de textes : longueur moyenne d'un document, en mots ~800 mots par document de documentation ; ~100 lignes par log.
Valeurs manquantes et doublons : nombre et traitement prévu Doublons possibles entre builds : déduplication par hash. Logs tronqués : signalés, exclus du jeu de test.
Découpage prévu : entraînement, test, évaluation Pas d'entraînement (RAG) ; 20–30 cas d'évaluation réservés, le reste indexé dans Chroma.
Script qui recalcule ces chiffres : chemin dans le dépôt scripts/dataset_stats.py

Dictionnaire des variables (une ligne par colonne utilisée) :

Variable Type (texte, nombre, catégorie, date) Signification Exemple de valeur Valeurs manquantes (%)
timestamp date Horodatage de la ligne de log 2026-11-16T10:23:45Z 0
step catégorie Étape du pipeline build, test, deploy 5
level catégorie Niveau de log ERROR, WARN, INFO 0
message texte Message de log ModuleNotFoundError: No module named 'foo' 0

Trois exemples tirés du jeu de données :

Exemple (entrée) Réponse ou étiquette attendue Nature de l'exemple : cas simple, cas difficile, cas limite
ModuleNotFoundError: No module named 'requests' Dépendance manquante → ajouter requests au requirements.txt Cas simple
Timeout after 3600s during test step Tests trop longs ou boucle infinie → vérifier les tests, augmenter le timeout Cas difficile
Log tronqué sans message d'erreur explicite Cause indéterminée → demander le log complet Cas limite

Limites connues du jeu de données (taille, déséquilibre entre classes, biais, données générées) : petite taille (~100 logs), formats hétérogènes selon la plateforme, biais vers les erreurs GitHub Actions, quelques logs tronqués. Alternative de repli : logs simulés à partir de scénarios d'échec typiques + documentation officielle publique.
